# Chain-of-Thought: фильтры списка задач

Сложная задача: студент должен быстро оставить на экране только нужные учебные задачи — по статусу, приоритету, предмету и строке поиска — и не потерять при этом просроченные.

Целиком промпт «сделай фильтры» слишком широкий: непонятно, фильтрует сервер или клиент, что делать с пустой выдачей и как проверять логику. Поэтому задача разрезана на четыре шага. Каждый шаг — отдельный промпт, результат предыдущего входит в контекст следующего.

## Шаг 1. Зафиксировать модель и границы

Промпт:

```text
Role: Ты технический ведущий проекта «Планёр».
Task: Определи модель фильтров списка задач и где их считать. Код не пиши.
Context: API уже отдаёт GET /api/tasks со всеми задачами одного пользователя. Задач мало, это личный список. Поля: status, priority, subject, title, description. Статусы todo | inProgress | done.
Format: 1) тип фильтра, 2) решение клиент или сервер и почему, 3) три правила сортировки, 4) что показать, если после фильтра ничего не осталось.
```

Результат шага:

- Фильтр: поиск (подстрока), статус, приоритет, предмет. Значение «все» сбрасывает ось.
- Считать на клиенте: список уже целиком на странице, переключение фильтра не должно ждать сеть. На API те же параметры оставлены, чтобы позже перенести отбор в SQL без смены привычки.
- Сортировка: невыполненные выше выполненных, внутри группы — по возрастанию срока.
- Пустая выдача при активном фильтре — отдельный текст «Ничего не нашлось», а не «Пока пусто».

## Шаг 2. Чистая функция

Промпт:

```text
Role: Ты Senior Frontend-разработчик. Следуй .cursorrules.
Task: Реализуй filterTasks, sortTasks и defaultFilters по решению из предыдущего шага.
Context: Тип StudyTask в frontend/src/types.ts. Поиск без учёта регистра по title, subject и description. Функция чистая, без DOM и fetch.
Format: Код в frontend/src/lib/tasks.ts и тест в frontend/src/test/tasks.test.ts: из двух задач остаётся одна, у которой status=todo и в названии есть «sql».
```

Результат: функции `filterTasks` и `sortTasks`, тест «оставляет задачи выбранного статуса и поискового запроса».

## Шаг 3. Интерфейс фильтров

Промпт:

```text
Role: Ты Senior Frontend-разработчик. Следуй .cursorrules.
Task: Собери панель фильтров и свяжи её со списком на главной странице.
Context: Модель — TaskFilters. Статус и приоритет — группы кнопок с aria-pressed. Предмет — select, пункты собираются из задач и заранее известных предметов. Поиск — отдельное поле над списком. На ширине меньше lg панель стоит над списком, на lg — слева колонкой 250px.
Format: Компонент frontend/src/components/TaskFilters.tsx и подключение в pages/BoardPage.tsx. Новых запросов к API не добавляй.
```

Результат: панель слева на десктопе и над списком на узком экране. Сводка считается по всем задачам, а не по отфильтрованным, чтобы цифры «всего» и «просрочено» не прыгали при поиске.

## Шаг 4. Проверка цепочки

Промпт:

```text
Role: Ты ревьюер.
Task: Проверь, что фильтр не противоречит правилам просрочки и пустых состояний.
Context: isOverdue возвращает false для status=done. Пустой список без фильтра и пустой результат фильтра — разные тексты. Ошибка сети не должна маскироваться текстом «Пока пусто».
Format: Короткий список дыр и минимальный патч, если дыра есть.
```

Найденная дыра: при ошибке загрузки и пустом массиве одновременно висели баннер ошибки и заглушка «Пока пусто». Патч в `BoardPage`: пустое состояние рисуется только если ошибки нет.

## Что дала цепочка

Пошаговые промпты удержали контракт (клиентский фильтр, серверные параметры не ломаем) и не дали смешать в одном ответе SQL, вёрстку и тесты. Каждый шаг проверяется отдельно: тип и решение, потом тест функции, потом экран, потом стык с ошибкой сети.
