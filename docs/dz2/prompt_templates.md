# Библиотека промпт-шаблонов

Шаблоны написаны для Cursor и проекта «Планёр». В каждом есть структура RTCF: Role, Task, Context, Format. В фигурных скобках — то, что подставляется перед отправкой.

## 1. Генерация компонента по описанию

```text
Role: Ты Senior Frontend-разработчик проекта «Планёр». Следуй .cursorrules.

Task: Создай компонент {имя компонента} по описанию: {что показывает и какие действия поддерживает}.

Context:
- Стек: React 19, TypeScript, Tailwind CSS 4.
- Типы задач уже есть в frontend/src/types.ts.
- Подписи статусов и приоритетов бери из frontend/src/lib/labels.ts.
- Тексты интерфейса на русском.
- Не используй any и не вызывай fetch из компонента.

Format:
- Именованный экспорт функционального компонента.
- Файл: frontend/src/components/{Имя}.tsx.
- Пропсы с явным типом.
- Состояния loading и error, если компонент сам ходит за данными. Если данные приходят пропсами, обработай пустой список.
- После кода напиши, как открыть компонент в интерфейсе.
```

Пример использования: «Создай компонент TaskCard. Карточка показывает предмет, приоритет, название, описание, срок и метку „Просрочено“, если задача не выполнена и дата раньше сегодня. Кнопки: следующий статус, изменить, удалить с подтверждением».

Результат лежит в `frontend/src/components/TaskCard.tsx`.

## 2. Рефакторинг с улучшением

```text
Role: Ты Senior Full-Stack разработчик. Следуй .cursorrules.

Task: Отрефактори {файл или функция}. Улучши {читаемость / разделение слоёв / обработку ошибок}, поведение для пользователя не меняй.

Context:
- Текущий код: {вставить код или указать путь}.
- Что считается поведением: {список сценариев, которые должны остаться}.
- Ограничения: без any, без новых библиотек, без смены JSON-контракта API.

Format:
- Покажи, что именно меняется и зачем, в 3–6 предложениях.
- Измени только затронутые файлы.
- Если логика чистая, обнови или добавь тест в frontend/src/test.
```

Пример: «Отрефактори разбор даты в formatDueDate. Сейчас дата может сдвигаться на сутки из-за UTC. Поведение: строка YYYY-MM-DD всегда форматируется как календарный день ru-RU».

Результат — `frontend/src/lib/dates.ts`.

## 3. Тесты для существующего кода

```text
Role: Ты инженер, который пишет тесты на Vitest и Testing Library. Следуй .cursorrules.

Task: Напиши тесты для {функция или компонент}.

Context:
- Файл реализации: {путь}.
- Позитивный сценарий: {что должно получиться}.
- Негативный сценарий: {какая ошибка или какой случай нельзя перепутать}.
- Тестовые данные клади в frontend/src/test/fixtures.ts, если они нужны больше чем в одном файле.
- Для компонентов оберни рендер в MemoryRouter, если внутри есть Link.

Format:
- Файл frontend/src/test/{имя}.test.ts или .tsx.
- Импортируй describe, it, expect из vitest.
- Названия тестов на русском, в терминах поведения, а не реализации.
- Не мокай то, что можно проверить напрямую.
```

Пример: «Напиши тесты для TaskCard: просроченная задача в статусе todo показывает „Просрочено“; выполненная задача с прошедшим сроком эту метку не показывает».

Результат — `frontend/src/test/TaskCard.test.tsx`.

## 4. Исправление ошибки

```text
Role: Ты разработчик, который чинит конкретный баг в «Планёре». Следуй .cursorrules.

Task: Исправь ошибку: {что происходит вместо ожидаемого}.

Context:
- Шаги воспроизведения: {1, 2, 3}.
- Ожидание: {как должно быть}.
- Факт: {текст из консоли, падающий тест или описание экрана}.
- Затронутые файлы, если известны: {пути}.

Format:
- Сначала назови причину в одном абзаце.
- Затем внеси минимальное исправление.
- Покажи, каким тестом или ручным шагом проверяется фикс.
- Не переписывай соседние функции.
```

Пример: «Второй тест TaskCard падает: выполненной задаче находится текст „Просрочено“. Шаги: npm test. Ожидание: у status=done метки нет. Факт: в DOM остаётся карточка из предыдущего теста».

Причина оказалась не в `isOverdue`, а в том, что Testing Library не очищала DOM между тестами Vitest. Исправление — `cleanup()` в `frontend/src/test/setup.ts`.

## 5. Декомпозиция сложной задачи

```text
Role: Ты технический ведущий. Следуй .cursorrules. Пока не пиши весь код.

Task: Разложи задачу «{формулировка}» на подзадачи, которые можно отдавать агенту по одной.

Context:
- Уже есть: {эндпоинты, типы, страницы}.
- Ограничение MVP: {что сознательно не делаем}.
- Стек менять нельзя.

Format:
- Нумерованный список из 3–7 шагов.
- У каждого шага: цель, файлы, критерий готовности.
- Отметь, какой шаг зависит от предыдущего.
- Код не пиши, пока не будет отдельного запроса на конкретный шаг.
```

Пример: «Разложи задачу „фильтры списка учебных задач“». Разложение и выполнение по шагам записаны в `docs/dz2/prompt_methodology.md`.
