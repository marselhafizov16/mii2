# Техническое задание: Планёр

Документ можно отдавать AI-агенту как контекст разработки. Реализация MVP лежит в `frontend/` и `backend/`.

## Описание проекта

Веб-приложение для личного списка учебных задач. Студент создаёт задачу, задаёт предмет, срок и приоритет, двигает статус и фильтрует список. Данные хранятся в PostgreSQL. Клиент на React не обращается к базе напрямую.

Вне скоупа: регистрация и роли, файлы, пуш-уведомления, календарь на месяц, совместное редактирование.

## Целевая аудитория

Один студент на своей машине или в учебном браузере. Интерфейс на русском. Предполагается десктоп и телефон: ширина от 360 px.

## Стек

- Клиент: React 19, TypeScript, Vite, Tailwind CSS 4, React Router 7.
- Сервер: ASP.NET Core 10, EF Core, Npgsql.
- База: PostgreSQL, имя базы `study_planner`, таблица `study_tasks`.
- Контракт JSON: camelCase. Статусы `todo | inProgress | done`. Приоритеты `low | medium | high`. Срок — `YYYY-MM-DD`.

## Функциональные требования

### Список и сводка

- `GET /api/tasks` возвращает задачи, по умолчанию упорядоченные по сроку.
- Необязательные query-параметры: `status`, `priority`, `subject`, `search`. Поиск — подстрока без учёта регистра по названию, предмету и описанию, спецсимволы `%` и `_` экранируются.
- Клиент дополнительно фильтрует уже загруженный список, чтобы переключение фильтра не ждало сеть.
- Сводка на клиенте: всего, к выполнению, в работе, просрочено. Просрочка: статус не `done` и календарный срок строго раньше сегодня. Сегодняшний день не просрочен.
- Выполненные задачи в списке ниже остальных.

### Создание и редактирование

- `POST /api/tasks` создаёт задачу. `PUT /api/tasks/{id}` заменяет поля.
- Название: обязательное, 3–120 символов после обрезки пробелов.
- Предмет: обязательный, 2–80 символов.
- Описание: необязательное, до 2000 символов.
- Срок обязателен. Приоритет и статус обязательны и входят в перечисления выше.
- Ответ 201 на создание содержит созданную задачу. Неизвестный id на изменение — 404 и сообщение «Задача не найдена».

### Статус и удаление

- `PATCH /api/tasks/{id}/status` с телом `{ "status": "..." }` меняет только статус.
- На карточке одно действие ведёт по цепочке todo → inProgress → done → todo. Подписи кнопок: «В работу», «Готово», «Вернуть».
- `DELETE /api/tasks/{id}` возвращает 204. В списке удаление только после подтверждения «Да».

### Карточка

- Маршрут `/tasks/:id`, данные через `GET /api/tasks/{id}`.
- Показывается полное описание, без обрезки в две строки, как в списке.

### Предметы

- Отдельной таблицы предметов нет. Подсказки формы и пункты фильтра собираются из задач плюс фиксированный набор: «Машинное обучение», «Базы данных», «Веб-разработка», «Алгоритмы».

## Нефункциональные требования

### Список и сводка

- Первая загрузка показывает состояние «Загружаем задачи…», а не пустой список до ответа.
- Сводка и фильтры остаются читаемыми на ширине 360 px: фильтры над списком, сводка сеткой 2×2. От `lg` фильтры — левая колонка.
- Поиск фильтрует без запроса на каждый символ.

### Создание и редактирование

- Ошибки полей видны текстом рядом с полем, не только цветом.
- Форма на узком экране открывается на всю ширину снизу, на широком — карточкой по центру.
- Пока запрос сохранения не завершён, повторная отправка отключена.

### Статус, удаление, карточка

- Кнопки действия на время запроса неактивны.
- Текст не вызывает горизонтальный скролл страницы.
- К фокусу у полей и кнопок есть видимое кольцо.

### API и данные

- Секретные данные в ответе об ошибке не возвращаются: без строки подключения и без стека.
- Пароль базы не хранится в git в боевом виде. В примере — `CHANGE_ME`.
- При пустой таблице инициализатор создаёт базу, если её нет, и добавляет демонстрационные задачи. Повторный запуск сиды не дублирует.
- CORS разрешён для `http://localhost:5173` и `http://127.0.0.1:5173`.

## Описание обработки ошибок

### Ошибки валидации

Сервер отвечает 400:

```json
{
  "message": "Проверьте поля формы",
  "errors": { "title": ["Название должно быть не короче 3 символов"] }
}
```

UX: общая фраза вверху формы и текст у конкретного поля. Форма не закрывается, введённые значения не стираются. Та же проверка выполняется в браузере до запроса, чтобы пустое название не ждало сеть.

### Нет данных

- Успешный пустой список: «Пока пусто» и пояснение, что задачу можно добавить.
- Фильтр отсёк все карточки: «Ничего не нашлось». Это не то же самое, что пустая база.
- Неизвестный id: «Задача не найдена» и ссылка на список.
- Пустое описание на карточке: фраза «Описание не добавлено», а не пустой блок без объяснения.

### Сетевые ошибки и недоступная база

- Браузер не достучался до API: «Нет соединения с сервером. Проверьте, что API запущен.» Кнопка «Повторить».
- PostgreSQL недоступен или пароль в строке подключения неверный: API отвечает 503 с коротким текстом про базу. Клиент показывает этот текст и «Повторить». Заглушка «Пока пусто» в этом случае не рисуется, чтобы не выглядело, будто задач правда нет.
- Сбой на смене статуса или удалении не затирает уже загруженный список. Меняется только баннер ошибки.

### Неавторизованный доступ

В MVP нет учётных записей, поэтому обычный сценарий до 401 не доходит. Контракт на будущее зафиксирован: если API ответит 401, клиент показывает «Нужно войти в аккаунт» и не подставляет демонстрационные чужие задачи. Сейчас эндпоинты открыты только потому, что приложение личное и локальное. Перед любым выносом в сеть нужен вход и фильтр задач по пользователю. До этого момента приложение не публикуется с боевой базой.

## Проверка полноты перед разработкой

Чеклист, которым сверялся агент:

- у каждой функции MVP есть история, критерий Given-When-Then и раздел в этом ТЗ;
- у каждого must-сценария есть негативная ветка: валидация, пусто, сеть или 404;
- статусы и имена полей в историях совпадают с JSON;
- адаптив назван в нефункциональных требованиях, а не оставлен «на потом»;
- секреты и персональные данные явно вынесены за скобки MVP.
